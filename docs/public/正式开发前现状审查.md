## 2. 保留、调整与退出正式实现的部分

| 处理 | 模块 | 建议及成本 |
|---|---|---|
| **保留** | `platform/windows.rs`、`platform/mod.rs`、`queue.rs`、`escape.rs`、`session.ts` | 保留已经跑通的系统接口、身份核验、取消边界和请求隔离。正式业务从外部接入，不把数据库塞进队列。成本低，重写风险反而高 |
| **保留并扩展** | `store.rs`、`paths.rs`、`assets.rs`、`scope.rs`、`migrations/` | 沿用单连接 SQLite、事务、原图共享和缓存授权。新增保存/草稿业务与后续迁移，不重建数据库工程。成本中 |
| **按用途复用** | 搜索、高亮、图片轮播、可见性加载、托盘与建窗 | 保留可用逻辑；分类筛选改稳定 ID，排序使用真实时间，调用后更新最近使用。窗口关闭在 B2 接入未保存保护。成本中 |
| **调整** | `App.tsx`、`types.ts`、窗口入口/CSS | 按主库/快捷面板拆入口组件，分离样式作用域；案例 DTO 补来源、时间、版本及引用行 ID，选中状态不用数组下标。随业务拆分，不一次性重构全部。成本中 |
| **退出正式 UI 依据** | 旧 PoC 主库 JSX、占位按钮、`poc.css` 的临时布局覆盖、样本排序语义 | 正式主库从定稿原型转换，不继续在错误 PoC 外观上堆补丁。历史文件和旧 exe 保留，替换完成后再决定清理。UI 还原属于主要开发工作 |
| **保留为开发工具** | manifest 导入、样本生成、旧报告/日志 | 不作为正式数据源，不默认导入合成案例。没有必要搬目录、改工程名或删除历史来表示“转正” |

特别注意：直接销毁主库/退出进程的现有行为适合只读 PoC，进入编辑阶段后必须保护未保存修改；这是必要业务调整，不是否定双窗口机制。原图输出与导入剪贴板图片是两个方向，后者新增入口，不重写前者。

## 3. 建议的正式实现方案

**继续使用 Tauri 2＋Rust＋React/TypeScript、rusqlite、原图目录和缩略图缓存。** 个人长期使用场景下，这个结构足够清晰；没有必要更换技术路线、引入 ORM/连接池、全局状态框架或复杂事件系统。

- **UI 来源明确**：V4.11 决定布局、比例、控件、图标和原位编辑；V5.0 补手动保存、琥珀草稿状态、未保存拦截、回收站与恢复确认。后续明确确认的快捷面板交互继续有效。`03_快捷调用面板早期样机.html` 和旧 PoC 不作为正式视觉依据。
- **直接做产品组件**：在现有应用中实现 `LibraryManager`、`CaseCard/Editor`、图片轨道和分类栏，接真实 SQLite。复用原型的样式与 SVG，逐块对照；不照搬原型的数组存储、localStorage、演示 JSON 备份、重置按钮和模拟异常入口。
- **先纠正发布样式入口**：将当前三元动态导入改为明确分支加载，限定主库/快捷面板样式范围；核对打包后的实际依赖。不能仅凭源码里写了 `library.css` 判断发布版已加载，也不为此先升级整套构建依赖。
- **保存由 Rust 负责**：图片就绪后，案例字段和关系一次事务提交，成功才显示已保存；React 保留编辑态，失败不丢输入。双窗用现有 Tauri 事件在提交后通知刷新，并在窗口重开时补拉，不新建事件总线。
- **按阶段补完整性**：B2 接草稿及统一离开拦截；D 按正式/草稿/回收站引用安全清理；E 使用 SQLite 一致性快照＋原图 ZIP，检查后整体恢复。完整切库仍留 E，不提前铺设恢复框架。

现有 schema 和路径入口可以承接上述业务。A 已生成的库要保留；新增字段通过后续版本迁移，不悄悄修改 v1 然后要求用户删库重来。缺图/外部损坏等错误需可理解地提示，不自动清空资料库。

## 4. 必要准备与推进顺序

保留原 A～F 的组织方式，但 A 作为已有基础，不再启动独立技术验证工程。

| 顺序 | 实际交付 | 验收重点 |
|---|---|---|
| 开始前的小步准备 | 经授权保存当前 A 源码快照；明确 V4.11/V5.0 对照点；真实数据与样本目录分离 | GitHub/本地版本边界清楚，旧成果可回退；无需另建 Demo |
| **B1：正式主库＋真实保存** | 先修样式加载并还原正式主库，再实现新建/编辑、手动保存、文件/拖放/Ctrl+V 图片、替换/排序、来源链接 | 发布 exe 外观对照定稿；新建→保存→重启仍在；共享图替换不伤其他案例；补一次 SQLite→文字/单图接入检查 |
| **B2：编辑安全闭环** | 自动草稿、异常恢复、放弃、搜索/切换/所有关闭入口保护 | 正式内容和草稿分离；失败保留输入；迟到导入不写错槽位、不复活已丢弃草稿 |
| **C：分类检索与调用** | 项目/标签、收藏、最近使用、持久偏好、双窗更新 | 改名不丢关系；调用仍常驻且保留位置；先覆盖常用豆包客户端，再补 ChatGPT Web/豆包 Web 的相关接收记录 |
| **D→E：删除与备份** | 回收站/撤销/共享图安全清理，再做 ZIP 备份恢复 | 只删除无引用文件；恢复失败不覆盖现库，往返后数据与原图一致 |
| **F：日常使用交付** | 安装升级、产品文案/版本整理、100/500 资源与响应基线 | 实际使用稳定、升级保数据；补相关缺口，不重跑未变化的全部测试 |

每次交付只记录改动、结果、未通过项及证据。涉及界面必须检查发布版外观；涉及写入/删除必须验证对应事务与引用边界。按你此前要求，实机视觉和目标应用操作由你完成，不启动 Computer Use。截图对照用于验收正式应用，不制作新的原型。

主要工作量在 **UI 准确还原、B2 编辑安全、E 恢复一致性**；现有 Windows 链路与 A 的复用价值很高。先完成少量卡片的真实保存闭环，再逐步接分类和安全功能，比同时铺开所有页面更易核对，也不会牺牲最终完整性。

1. **下一轮实施范围**：建议批准 B1，包含当前样式缺陷修复、正式主库还原及真实保存闭环；把 A 尚缺的接入冒烟并入验收。暂不同时展开 B2～F。取舍是先交付能实际保存的正式界面，草稿异常恢复仍要等 B2。
